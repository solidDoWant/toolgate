# Gateway configuration reference

For: admins who deploy the toolgate gateway.

This page is generated from the code by `make generate-docs`. Do not edit it by hand.

The gateway reads its configuration when `toolgate serve` starts, in this order:

1. The default value of each setting.
2. The YAML file named by the `--config` flag, or else by the `TOOLGATE_CONFIG` environment variable. The file is optional. An unknown key in the file is an error.
3. The environment variables. A variable that is set and not empty replaces the value from the file.

If a setting is missing or not valid, the gateway does not start. It prints one line for each problem and exits with code 1.

| YAML key | Environment variable | Default | Description |
|---|---|---|---|
| `listenAddress` | `TOOLGATE_LISTEN_ADDRESS` | `:8080` | The address where the gateway listens for MCP and API requests and for the `/healthz` and `/readyz` probes. |
| `metricsListenAddress` | `TOOLGATE_METRICS_LISTEN_ADDRESS` | `:9090` | The address of the separate listener that serves Prometheus metrics at `/metrics`. It must differ from `listenAddress`. |
| `databaseURL` | `TOOLGATE_DATABASE_URL` | none | The PostgreSQL connection string, as a URL or as key/value pairs. Required. When it starts, the gateway creates and updates its tables in this database. If it cannot, it stops with an error. `/readyz` answers 503 while the gateway cannot connect to this database. |
| `migrateOnStart` | `TOOLGATE_MIGRATE_ON_START` | `true` | Whether the gateway creates and updates its tables when it starts. If it is `false`, the gateway does not change the schema. Before it opens its listeners, it checks that the database schema is at the version it needs. If the schema is older, or has no tables yet, the gateway logs a message and exits with code 1. Run `toolgate migrate`, or let the chart's migration Job run, before you start the gateway. Use `false` when the gateway's database user has data rights only. A schema that is newer than the gateway (after a rollback) is only logged. |
| `shutdownTimeout` | `TOOLGATE_SHUTDOWN_TIMEOUT` | `30s` | After SIGTERM, the gateway stops accepting requests and waits this long for open requests to finish. Then it stops. Write it as a Go duration, such as `30s`. |
| `logLevel` | `TOOLGATE_LOG_LEVEL` | `info` | The lowest level of the JSON log lines that the gateway writes to stdout: `debug`, `info`, `warn` or `error`. |
| `otlpEndpoint` | `TOOLGATE_OTLP_ENDPOINT` | none | The OTLP/HTTP endpoint that receives the traces of the gateway, such as `http://otel-collector:4318`. The gateway sends traces to `/v1/traces` under this URL. If it is empty, the gateway does not export traces. |
| `otlpIngest` | `TOOLGATE_OTLP_INGEST` | none | When it is `true`, the gateway accepts OpenTelemetry data from signed-in clients at `POST /v1/traces`, `/v1/metrics` and `/v1/logs`. It forwards the data to `otlpEndpoint`, so `otlpEndpoint` is required. The gateway removes the identity attributes that the client sent. These are the attributes whose name starts with `user_`, `enduser_` or `workspace_` after each character outside `[A-Za-z0-9]` changes to `_` and the name changes to lower case. Then the gateway sets `user.id`, `enduser.id`, `user.email` and `workspace.id` from the verified identity. A request body can be 4 MiB at most, and each replica handles 4 requests at the same time at most. When it is `false`, these paths answer 404. |
| `telemetry.allowContent` | `TOOLGATE_TELEMETRY_ALLOW_CONTENT` | none | When it is `true`, the gateway keeps prompt and tool content in the OpenTelemetry data that clients send to it. Prompts, tool inputs and tool output are examples of this content. Clients add it when users set `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS` or `OTEL_LOG_TOOL_CONTENT`. When it is `false`, the gateway removes it. Set it to `true` only when the telemetry backend is allowed to hold user content. The gateway then sends that content to the backend. |
| `oidcIssuerURL` | `TOOLGATE_OIDC_ISSUER_URL` | none | The issuer URL of the OIDC identity provider (IdP) that users sign in with, such as `https://idp.example.com/realms/main`. Required. The gateway reads the IdP's discovery document and signing keys from it, and accepts only access tokens this issuer signed. |
| `oidcAudience` | `TOOLGATE_OIDC_AUDIENCE` | none | The audience that users' access tokens must contain, such as `toolgate`. Required. The gateway refuses a token for another audience. |
| `oidcEmailClaim` | `TOOLGATE_OIDC_EMAIL_CLAIM` | `email` | The access token claim that holds the user's email address. |
| `oidcEmailVerifiedClaim` | `TOOLGATE_OIDC_EMAIL_VERIFIED_CLAIM` | `email_verified` | The access token claim that tells whether the IdP verified the email address. The gateway uses the email only when this claim is `true`. |
| `oidcGroupsClaim` | `TOOLGATE_OIDC_GROUPS_CLAIM` | `groups` | The access token claim that holds the user's groups, as a list of strings. The gateway refuses a token if this claim has another type. |
| `oidcCLIClientID` | `TOOLGATE_OIDC_CLI_CLIENT_ID` | none | The client ID that `toolgate login` signs in with, such as `toolgate-cli`. It must be a public client (one without a secret) with the OAuth 2.0 device authorization grant. The gateway publishes it, with `oidcIssuerURL`, `oidcCLIScopes` and `oidcEmailClaim`, at `/.well-known/toolgate-client` without authentication. If it is empty, users must pass `--client-id` to `toolgate login`. |
| `oidcCLIScopes` | `TOOLGATE_OIDC_CLI_SCOPES` | `["openid","email","profile","offline_access"]` | The scopes that `toolgate login` asks for. In the environment variable, separate the scopes with commas. Keep `offline_access`: without it, the IdP gives no refresh token and users must sign in again when their access token expires. |
| `serviceAccountNamespaces` | `TOOLGATE_SERVICE_ACCOUNT_NAMESPACES` | none | The namespaces whose pods may sign in with a Kubernetes service-account token, such as `[ci, agents]`. In the environment variable, separate the names with commas. A pod signs in with a projected token for the audience `toolgate`, and its workspace is the pod's owner. If the list is empty, only users can sign in. |
| `secretsKeysetFile` | `TOOLGATE_SECRETS_KEYSET_FILE` | none | The path of the Tink keyset that encrypts user secrets, in the JSON keyset format of Tink. Mount it from a Kubernetes Secret. It is never stored in PostgreSQL. The gateway serves the secrets API (`/api/v1/secrets`) only when this is set. `toolgate admin rewrap` needs it too. See [User secrets](user-secrets.md). |
| `leaseNamespace` | `TOOLGATE_LEASE_NAMESPACE` | none | The namespace of the Lease that picks the one replica that runs the runtime reconciler, normally the gateway's own namespace. The chart sets it. If it is empty, the gateway runs without Kubernetes: it serves requests but never starts or stops MCP servers. |
| `catalogNamespaces` | `TOOLGATE_CATALOG_NAMESPACES` | none | The namespaces whose `MCPServerTemplate` and `ToolgateRule` objects the gateway reads, such as `[toolgate-catalog]`. In the environment variable, separate the names with commas. Objects in other namespaces are ignored. If the list is empty, the gateway reads only `leaseNamespace`. The gateway reads no catalog without `leaseNamespace`. |
| `gatewayPodLabels` | `TOOLGATE_GATEWAY_POD_LABELS` | none | The labels of the gateway's own pods, as `key=value` items, such as `[app.kubernetes.io/name=toolgate]`. In the environment variable, separate the items with commas. Each MCP server's network policy accepts connections only from pods in `leaseNamespace` with these labels. Required with `leaseNamespace`. The chart sets it. |
| `sharedNamespace` | `TOOLGATE_SHARED_NAMESPACE` | none | The namespace where the MCP servers of `namespace: shared` templates run, all together. The chart sets it from `config.sharedNamespace.name`. The namespace must exist and carry the labels `toolgate.soliddowant.dev/writable: "true"` and `pod-security.kubernetes.io/enforce: restricted`. The gateway never creates, labels or deletes it. It must not start with `tg-`, the prefix of the namespaces the gateway makes for single servers. If it is empty, every `namespace: shared` template is invalid. |
| `instanceLimitPerUser` | `TOOLGATE_INSTANCE_LIMIT_PER_USER` | `20` | The maximum number of MCP server instances that run for one user at the same time. Per-session and per-user instances count for the user who started them. Shared instances do not count. When a user is at the limit, an enable that must start a new instance fails. An enable of a server that already runs for the user still works. At least 1. The chart sets it from `config.limits.instancesPerUser`. |
| `instanceLimit` | `TOOLGATE_INSTANCE_LIMIT` | `200` | The maximum number of MCP server instances that the gateway runs at the same time, for all users and shared instances together. At the limit, an enable that must start a new instance fails. At least 1. The chart sets it from `config.limits.instances`. |
| `sessionIdleTimeout` | `TOOLGATE_SESSION_IDLE_TIMEOUT` | `2h0m0s` | How long a session can go without requests before the gateway ends it. Ending a session disables all of its servers, so its per-session MCP servers stop. A later request with the same session ID starts the session again with no servers enabled. The gateway checks every 30 seconds. Write it as a Go duration, such as `2h`. It must be more than zero. The chart sets it from `config.sessionIdleTimeout`. |
| `publicURL` | `TOOLGATE_PUBLIC_URL` | none | The URL where users reach the gateway in a browser, such as `https://toolgate.example.com`. Required when `oidcUIClientID` is set. It must be `https://`; `http://localhost` and `http://127.0.0.1` are accepted for tests only. The web UI's sign-in redirect URI is this URL plus `/ui/auth/callback`. |
| `oidcUIClientID` | `TOOLGATE_OIDC_UI_CLIENT_ID` | none | The client ID that the web UI signs users in with, using the authorization code grant with PKCE. It is a separate client from `oidcCLIClientID`, and the IdP must allow the redirect URI `publicURL` plus `/ui/auth/callback`. Both clients must give a user the same subject (`sub`). The web UI is on only when this is set. |
| `oidcUIClientSecretFile` | `TOOLGATE_OIDC_UI_CLIENT_SECRET_FILE` | none | The path of a file that holds the web UI client's secret. Mount it from a Kubernetes Secret. If it is empty, the web UI is a public client (without a secret). PKCE is used in both cases. |
| `oidcUIScopes` | `TOOLGATE_OIDC_UI_SCOPES` | `["openid","email","profile"]` | The scopes that the web UI asks for at sign-in. In the environment variable, separate the scopes with commas. The IdP must put the email and groups claims in the ID token. |
| `adminGroup` | `TOOLGATE_ADMIN_GROUP` | none | The group whose members are web UI admins, checked against the groups from the user's sign-in. Group changes take effect at the latest when the 8-hour UI session ends. Members who sign in as users, not service accounts, also see the audit events of all users in `toolgate audit tail`; there the group is checked on each request. If it is empty, nobody is an admin. |
| `approvalTimeout` | `TOOLGATE_APPROVAL_TIMEOUT` | `10m0s` | How long a call that needs approval waits for a person to approve it, and how long an approved request stays usable. The gateway marks a waiting request expired 1 minute after this time has passed. Write it as a Go duration, such as `10m`. It must be from 1 minute to 1 hour. The chart sets it from `config.ui.approvalTimeout`. |
| `auditPayloads` | `TOOLGATE_AUDIT_PAYLOADS` | none | Whether the gateway stores audit payloads: the arguments of each tool call and approval request, and each tool result. A payload under 64 KiB (65,536 bytes) is stored in its audit row in PostgreSQL. A larger one is stored as an object in `auditS3Bucket`. If this is `false`, no arguments or results are stored. If it is `true`, `auditS3Bucket` is required. The chart sets it from `config.audit.payloads`. |
| `auditS3Endpoint` | `TOOLGATE_AUDIT_S3_ENDPOINT` | none | The URL of the S3 API that stores large audit payloads, such as `https://s3.example.com`. If it is empty, the gateway uses the AWS S3 endpoint of `auditS3Region`. The gateway gets its S3 credentials from the default chain of the AWS SDK, such as the `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` environment variables. The chart sets it from `config.audit.s3.endpoint`. |
| `auditS3Region` | `TOOLGATE_AUDIT_S3_REGION` | none | The S3 region of `auditS3Bucket`, such as `us-east-1`. The chart sets it from `config.audit.s3.region`. |
| `auditS3Bucket` | `TOOLGATE_AUDIT_S3_BUCKET` | none | The S3 bucket that stores large audit payloads. Required when `auditPayloads` is `true`. If the bucket has object lock, the gateway locks each object in governance mode for the audit retention time. Add a lifecycle rule under `auditS3Prefix` that expires current objects and noncurrent versions after the retention time plus a margin. The chart sets it from `config.audit.s3.bucket`. |
| `auditS3Prefix` | `TOOLGATE_AUDIT_S3_PREFIX` | none | The prefix of the object keys of audit payloads, such as `toolgate/`. Each key is `<prefix>payloads/<yyyy>/<mm>/<dd>/<uuid>.json`. The chart sets it from `config.audit.s3.prefix`. |
| `auditS3PathStyle` | `TOOLGATE_AUDIT_S3_PATH_STYLE` | none | Whether the gateway puts the bucket name in the URL path (`https://s3.example.com/bucket/key`) instead of the host name. Many S3-compatible servers need `true`. The chart sets it from `config.audit.s3.pathStyle`. |
| `resolvers` | `` | none | The HTTP services a template's `${resolver:<name>}` gets a value from. Set it in the YAML file only. Each item has a `name` (lowercase letters, digits and `-`, starting with a letter, at most 63 characters), a `url` that must be `https://`, an `audience` for the service-account token the gateway sends, a `timeout` (a Go duration, default `10s`, at most `60s`) and an optional `caFile`, a PEM file of the certificate authorities that sign the resolver's certificate. The gateway reads the token from `/var/run/secrets/toolgate/resolvers/<name>/token` for each request. The chart sets it from `config.resolvers` and mounts each token. |
| `spiffeTrustDomains` | `` | none | The SPIFFE trust domains whose JWT-SVIDs may sign in. Set it in the YAML file only. Each item has a `name` (the trust domain, such as `coder.example.com`), exactly one of `bundleEndpointURL` (a SPIFFE bundle endpoint with the `https_web` profile) and `jwksURL` (a JWKS document, such as that of SPIRE's OIDC discovery provider), both `https://`, and an optional `caFile`, a PEM file of private certificate authorities added to the system ones. This list is the only gateway-level allow-list for SPIFFE IDs. The chart sets it from `config.spiffe.trustDomains`. |
| `workspaceAttestation` | `` | none | Attested user sessions: a user's token plus a workload token from a workspace pod or a SPIFFE workload, bound to that user, so the session's workspace is verified. Set it in the YAML file only; the chart sets it from `config.workspaceAttestation`. Off when absent: the `X-Toolgate-Attestation` header is then ignored. `namespaces` (required) lists the namespaces whose service-account tokens may attest a user; it is separate from `serviceAccountNamespaces`. `keys` names the pod label keys (annotations are read when a label is missing) of `userID`, `email`, `username` and `workspace`; they default to Coder's `com.coder.user.id`, `com.coder.user.email`, `com.coder.user.username` and `com.coder.workspace.name`. `match.by` is `email` (the pod's email must equal the user's verified email, ignoring case) or `claim` (the user token's `match.claim` must be a string equal to the pod's `match.key`, `userID` or `username`). `workspaceID` (required) is the verified workspace, such as `coder/{username}/{workspace}`; it may use `{userID}`, `{username}` and `{workspace}`, must start with a literal segment that isn't `claimed`, `k8s` or empty, and is at most 256 characters once rendered. `spiffeIDPattern`, if set, also accepts JWT-SVIDs whose ID matches it, such as `spiffe://coder.example.com/coder/{username}/{workspace}`: its trust domain must be in `spiffeTrustDomains`, each placeholder is one whole path segment, `match.by` must be `claim`, and it must contain `{<match.key>}` and every placeholder `workspaceID` uses. |
