# Gateway configuration reference

For: admins who deploy the toolgate gateway.

This page is generated from the code by `make generate-docs`. Do not edit it by hand.

The gateway reads its configuration when `toolgate serve` starts, in this order:

1. The default value of each setting.
2. The YAML file named by the `--config` flag, or else by the `TOOLGATE_CONFIG` environment variable. The file is optional. An unknown key in the file is an error.
3. The environment variables. A variable that is set and not empty replaces the value from the file.

If a setting is missing or not valid, the gateway does not start. It prints one line for each problem and exits with code 1.

| YAML key | Environment variable | Default | Description |
|---|---|---|---|
| `-` | `` | none | IgnoredSettings names removed settings that the file or environment still set. Load ignores them; `toolgate serve` logs a warning. |
| `listenAddress` | `TOOLGATE_LISTEN_ADDRESS` | `:8080` | The address where the gateway listens for MCP and API requests and for the `/healthz` and `/readyz` probes. |
| `metricsListenAddress` | `TOOLGATE_METRICS_LISTEN_ADDRESS` | `:9090` | The address of the separate listener that serves Prometheus metrics at `/metrics`. It must differ from `listenAddress`. |
| `databaseURL` | `TOOLGATE_DATABASE_URL` | none | The PostgreSQL connection string, as a URL or as key/value pairs. Required. When it starts, the gateway creates and updates its tables in this database. If it cannot, it stops with an error. `/readyz` answers 503 while the gateway cannot connect to this database. |
| `migrateOnStart` | `TOOLGATE_MIGRATE_ON_START` | `true` | Whether the gateway creates and updates its tables when it starts. If it is `false`, the gateway does not change the schema. Before it opens its listeners, it checks that the database schema is at the version it needs. If the schema is older, or has no tables yet, the gateway logs a message and exits with code 1. Run `toolgate migrate`, or let the chart's migration Job run, before you start the gateway. Use `false` when the gateway's database user has data rights only. A schema that is newer than the gateway (after a rollback) is only logged. |
| `shutdownTimeout` | `TOOLGATE_SHUTDOWN_TIMEOUT` | `30s` | After SIGTERM, the gateway stops accepting requests and waits this long for open requests to finish. Then it stops. Write it as a Go duration, such as `30s`. |
| `logLevel` | `TOOLGATE_LOG_LEVEL` | `info` | The lowest level of the JSON log lines that the gateway writes to stdout: `debug`, `info`, `warn` or `error`. |
| `otlpEndpoint` | `TOOLGATE_OTLP_ENDPOINT` | none | The OTLP/HTTP base URL that receives OpenTelemetry data, such as `http://otel-collector:4318`. It sets any of `otlp.metricsEndpoint`, `otlp.logsEndpoint` and `otlp.tracesEndpoint` that you leave empty, so all three kinds of data go to one place. The gateway adds `/v1/metrics`, `/v1/logs` or `/v1/traces` to the URL. |
| `otlp.metricsEndpoint` | `TOOLGATE_OTLP_METRICS_ENDPOINT` | none | The OTLP/HTTP base URL that receives metrics, such as `http://victoria-metrics:8428/opentelemetry`. The gateway sends metrics to `/v1/metrics` under this URL. If it and `otlpEndpoint` are empty, the gateway accepts metrics from clients and discards them. |
| `otlp.logsEndpoint` | `TOOLGATE_OTLP_LOGS_ENDPOINT` | none | The OTLP/HTTP base URL that receives logs, such as `http://victoria-logs:9428/insert/opentelemetry`. The gateway sends logs to `/v1/logs` under this URL. If it and `otlpEndpoint` are empty, the gateway accepts logs from clients and discards them. The value `stdout` writes each received log record to the gateway's standard output as one JSON line instead, for the cluster's log pipeline to collect. |
| `otlp.tracesEndpoint` | `TOOLGATE_OTLP_TRACES_ENDPOINT` | none | The OTLP/HTTP base URL that receives traces, including the gateway's own traces. The gateway sends traces to `/v1/traces` under this URL. If it and `otlpEndpoint` are empty, the gateway does not export its own traces, and it accepts traces from clients and discards them. |
| `telemetry.dropSessionIdFromMetrics` | `TOOLGATE_TELEMETRY_DROP_SESSION_ID_FROM_METRICS` | none | When it is `true`, the gateway removes the `session.id` attribute from metric data points that clients send, so the metrics backend stores a bounded set of series. Logs and traces keep `session.id`. Data points that become identical are combined into one. When it is `false`, metrics keep `session.id`. Don't use it when sessions run at the same time with the same user, workspace and model: their counters share a series and the totals come out too high. |
| `otlpIngest` | `TOOLGATE_OTLP_INGEST` | none | When it is `true`, the gateway accepts OpenTelemetry data from signed-in clients at `POST /v1/traces`, `/v1/metrics` and `/v1/logs`. It forwards each kind of data to its own endpoint (`otlp.metricsEndpoint`, `otlp.logsEndpoint`, `otlp.tracesEndpoint`, each defaulting to `otlpEndpoint`). Data of a kind with no endpoint is accepted and discarded. The gateway removes the identity attributes that the client sent. These are the attributes whose name starts with `user_`, `enduser_` or `workspace_` after each character outside `[A-Za-z0-9]` changes to `_` and the name changes to lower case. Then the gateway sets `user.id`, `enduser.id`, `user.email` and `workspace.id` from the verified identity. A request body can be 4 MiB at most, and it must arrive within 10 seconds, or the gateway answers 408. Each replica handles 4 requests at the same time at most. When it is `false`, these paths answer 404. |
| `telemetry.allowContent` | `TOOLGATE_TELEMETRY_ALLOW_CONTENT` | none | When it is `true`, the gateway keeps prompt and tool content in the OpenTelemetry data that clients send to it. Prompts, tool inputs and tool output are examples of this content. Clients add it when users set `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS` or `OTEL_LOG_TOOL_CONTENT`. Session titles, which the plugin sends, are content too. When it is `false`, the gateway removes it. Set it to `true` only when the telemetry backend is allowed to hold user content. The gateway then sends that content to the backend. |
| `oidcIssuerURL` | `TOOLGATE_OIDC_ISSUER_URL` | none | The issuer URL of the OIDC identity provider (IdP) that users sign in with, such as `https://idp.example.com/realms/main`. Required. The gateway reads the IdP's discovery document and signing keys from it, and accepts only access tokens this issuer signed. |
| `oidcAudience` | `TOOLGATE_OIDC_AUDIENCE` | none | The audiences that users' access tokens may be for, such as `toolgate` or `[toolgate, coder-toolgate]`: one value or a list of 1 to 8. Each is the client ID of an OIDC client at the `oidcIssuerURL` provider, and is at most 256 characters long. Required. In the environment variable, separate the audiences with commas. The gateway accepts a token that has at least one of these audiences, and refuses a token for none of them. Every audience is a client whose access tokens the gateway accepts, so list only clients made for toolgate. |
| `oidcAdditionalIssuers` | `` | none | More OIDC issuers whose access tokens the gateway accepts, for an IdP that gives each client its own issuer (Authentik does). Set it in the YAML file only; the chart sets it from `config.oidc.additionalIssuers`. At most 8 items. Each has an `issuerURL` (an http or https URL, exactly as in its tokens' `iss` claim, different from `oidcIssuerURL` and from the other items) and an `audience` (one value or a list of 1 to 8, with the same rules as `oidcAudience`). The gateway picks the issuer by the token's `iss` claim and checks the token with that issuer's signing keys and audiences. The claim settings below apply to every issuer, and the user is the token's `sub` claim, so every issuer must give one person the same `sub`. `oidcIssuerURL` stays the issuer that `toolgate login` and the web UI use. The gateway reads each additional issuer's discovery document when a token first names it, so an issuer that is down refuses only its own tokens. |
| `oidcEmailClaim` | `TOOLGATE_OIDC_EMAIL_CLAIM` | `email` | The access token claim that holds the user's email address. |
| `oidcEmailVerifiedClaim` | `TOOLGATE_OIDC_EMAIL_VERIFIED_CLAIM` | `email_verified` | The access token claim that tells whether the IdP verified the email address. The gateway uses the email only when this claim is `true`. |
| `oidcGroupsClaim` | `TOOLGATE_OIDC_GROUPS_CLAIM` | `groups` | The access token claim that holds the user's groups, as a list of strings. The gateway refuses a token if this claim has another type. |
| `oidcCLIClientID` | `TOOLGATE_OIDC_CLI_CLIENT_ID` | none | The client ID that `toolgate login` signs in with, such as `toolgate-cli`. It must be a public client (one without a secret) with the OAuth 2.0 device authorization grant. The gateway publishes it, with `oidcIssuerURL`, `oidcCLIScopes` and `oidcEmailClaim`, at `/.well-known/toolgate-client` without authentication. If it is empty, users must pass `--client-id` to `toolgate login`. |
| `oidcCLIScopes` | `TOOLGATE_OIDC_CLI_SCOPES` | `["openid","email","profile","offline_access"]` | The scopes that `toolgate login` asks for. In the environment variable, separate the scopes with commas. Keep `offline_access`: without it, the IdP gives no refresh token and users must sign in again when their access token expires. |
| `serviceAccountNamespaces` | `TOOLGATE_SERVICE_ACCOUNT_NAMESPACES` | none | The namespaces whose pods may sign in with a Kubernetes service-account token, such as `[ci, agents]`. In the environment variable, separate the names with commas. A pod signs in with a projected token for the audience `toolgate`, and its workspace is the pod's owner. If the list is empty, only users can sign in. |
| `secretsKeysetFile` | `TOOLGATE_SECRETS_KEYSET_FILE` | none | The path of the Tink keyset that encrypts user secrets, in the JSON keyset format of Tink. Mount it from a Kubernetes Secret. It is never stored in PostgreSQL. The gateway serves the secrets API (`/api/v1/secrets`) only when this is set. `toolgate admin rewrap` needs it too. See [User secrets](user-secrets.md). |
| `leaseNamespace` | `TOOLGATE_LEASE_NAMESPACE` | none | The namespace of the Lease that picks the one replica that runs the runtime reconciler, normally the gateway's own namespace. The chart sets it. If it is empty, the gateway runs without Kubernetes: it serves requests but never starts or stops MCP servers. |
| `catalogNamespaces` | `TOOLGATE_CATALOG_NAMESPACES` | none | The namespaces whose `MCPServerTemplate` and `ToolgateRule` objects the gateway reads, such as `[toolgate-catalog]`. In the environment variable, separate the names with commas. Objects in other namespaces are ignored. If the list is empty, the gateway reads only `leaseNamespace`. The gateway reads no catalog without `leaseNamespace`. |
| `gatewayPodLabels` | `TOOLGATE_GATEWAY_POD_LABELS` | none | The labels of the gateway's own pods, as `key=value` items, such as `[app.kubernetes.io/name=toolgate]`. In the environment variable, separate the items with commas. Each MCP server's network policy accepts connections only from pods in `leaseNamespace` with these labels. Required with `leaseNamespace`. The chart sets it. |
| `sharedNamespace` | `TOOLGATE_SHARED_NAMESPACE` | none | The namespace where the MCP servers of `namespace: shared` templates run, all together. The chart sets it from `config.sharedNamespace.name`. The namespace must exist and carry the labels `toolgate.soliddowant.dev/writable: "true"` and `pod-security.kubernetes.io/enforce: restricted`. The gateway never creates, labels or deletes it. It must not start with `tg-`, the prefix of the namespaces the gateway makes for single servers. If it is empty, every `namespace: shared` template is invalid. |
| `templateSecretsNamespace` | `TOOLGATE_TEMPLATE_SECRETS_NAMESPACE` | none | The namespace that holds the Secrets that templates read with `${templateSecret:NAME/KEY}`. The chart sets it from `config.templateSecretsNamespace` and gives the gateway read access to Secrets in this namespace only. The admin creates the namespace and its Secrets, and must not label it `toolgate.soliddowant.dev/writable`. It must be a namespace name that does not start with `tg-`, and it must not be `leaseNamespace`, `sharedNamespace`, `kube-system` or one of `catalogNamespaces`. If it is empty, the feature is off. |
| `instanceLimitPerUser` | `TOOLGATE_INSTANCE_LIMIT_PER_USER` | `20` | The maximum number of MCP server instances that run for one user at the same time. Per-session and per-user instances count for the user who started them. Shared instances do not count. When a user is at the limit, an enable that must start a new instance fails. An enable of a server that already runs for the user still works. At least 1. The chart sets it from `config.limits.instancesPerUser`. |
| `instanceLimit` | `TOOLGATE_INSTANCE_LIMIT` | `200` | The maximum number of MCP server instances that the gateway runs at the same time, for all users and shared instances together. At the limit, an enable that must start a new instance fails. At least 1. The chart sets it from `config.limits.instances`. |
| `sessionIdleTimeout` | `TOOLGATE_SESSION_IDLE_TIMEOUT` | `2h0m0s` | How long a session can go without requests before the gateway ends it. An ended session keeps its list of enabled servers for `sessionResumeWindow`, but its per-session MCP servers stop. A later request with the same session ID starts the session again with no servers enabled. The gateway checks every 30 seconds. Write it as a Go duration, such as `2h`. It must be more than zero. The chart sets it from `config.sessionIdleTimeout`. |
| `sessionResumeWindow` | `TOOLGATE_SESSION_RESUME_WINDOW` | `24h0m0s` | How long the gateway keeps the list of enabled servers of a session that ended. It must be from `1h` to `168h` (7 days). The chart sets it from `config.sessionResumeWindow`. |
| `publicURL` | `TOOLGATE_PUBLIC_URL` | none | The URL where users reach the gateway in a browser, such as `https://toolgate.example.com`. Required when `oidcUIClientID` is set. | `mcpPublicURL` | `TOOLGATE_MCP_PUBLIC_URL` | none | The URL of the MCP endpoint as MCP clients on the internet reach it, such as `https://mcp.example.com/mcp`. It must be `https://`; `http://localhost` and `http://127.0.0.1` are accepted for tests only. If it is empty, it is `publicURL` plus `/mcp`. If both are empty, the gateway serves no metadata. | `oidcUIClientID` | `TOOLGATE_OIDC_UI_CLIENT_ID` | none | The client ID that the web UI signs users in with, using the authorization code grant with PKCE. | `oidcUIClientSecretFile` | `TOOLGATE_OIDC_UI_CLIENT_SECRET_FILE` | none | The path of a file that holds the web UI client's secret. Mount it from a Kubernetes Secret. If it is empty, the web UI is a public client (without a secret). PKCE is used in both cases. |
| `oidcUIScopes` | `TOOLGATE_OIDC_UI_SCOPES` | `["openid","email","profile"]` | The scopes that the web UI asks for at sign-in. In the environment variable, separate the scopes with commas. The IdP must put the email and groups claims in the ID token. |
| `adminGroup` | `TOOLGATE_ADMIN_GROUP` | none | The group whose members are web UI admins, checked against the groups from the user's sign-in.
